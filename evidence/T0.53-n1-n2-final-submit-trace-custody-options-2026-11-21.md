## A. ¿Qué significa realmente final_turn? Verificado en fuentes originales

Fuente [SciResearch-Eval harness.py @9d391b3](https://github.com/Btwestyo/sciresearch-eval/blob/9d391b3aa8daf8d0b944acda12c7f8b089a1d8e0/src/sciresearch_eval/agents/harness.py), Git blob `194a4b36caf4cd702caee34044ec457247644aee`, líneas aprox.250–345:

1. Antes de cada request calcula `total_in=usage["input_tokens"]+usage["cache_read_tokens"]+usage["cache_write_tokens"]`. Si `turns>=MAX_TURNS` o `total_in>=max_input_tokens`, activa una sola `final_turn` adicional, informa al modelo que llame submit y reduce `specs` a `submit`. Un nuevo paso tras esa oportunidad termina `limit_turns_or_tokens`.
2. Solicita al adapter `agent.converse(... force_tool="submit")`, pero el [adaptador fuente](https://github.com/Btwestyo/sciresearch-eval/blob/9d391b3aa8daf8d0b944acda12c7f8b089a1d8e0/src/sciresearch_eval/agents/openai_backend.py), Git blob `62226f9e814af28593763281ed8cf5e25dc6cc5d`, implementa este pedido vía `tool_choice`. **La copia T0.52** [controller](../scripts/h0_sciresearch_qwen_t052.py), Git blob `baa40653c60f51d6dac3152098fc6a564162f3c2`, **quita el campo tool_choice** por limitación del transporte de Ollama pin0.40.16. De ello se infiere que `force_tool` **no se impone a nivel de transporte** en esta copia; ofrecer solo la herramienta submit no obliga al modelo a invocarla.
3. El harness cuenta la respuesta del modelo como turno aun si no contiene `toolUse`; puede emitir un recordatorio o agotar la oportunidad. `tools.submitted` solo pasa a verdadero si `tools.call("submit", ...)` logra completar y `env.submit` registra la entrega. El [grader original](https://github.com/Btwestyo/sciresearch-eval/blob/9d391b3aa8daf8d0b944acda12c7f8b089a1d8e0/src/sciresearch_eval/grader.py), Git blob `8194044d11b17b6d9d2b040a5115ff35bb798b64`, devuelve `{"submitted":false}` cuando no hay `env.submission`; un proceso exitoso o `REQUEST_COMPLETED` no equivale a puntuación.
4. T0.38 [guard de categorías](../scripts/h0_limit_guard_t038.py), Git blob `e2038970b985075f3c5b18e981919dff0b1886a5`, **solo añade metadatos de causa** y no cambia stop/dispatch. No hubo cap duro de 24k.

## C. Cuál traza existe y cuál falta

El [harness original](https://github.com/Btwestyo/sciresearch-eval/blob/9d391b3aa8daf8d0b944acda12c7f8b089a1d8e0/src/sciresearch_eval/agents/harness.py) escribe en el directorio de ejecución `transcript.json`, `env_trace.json`, `state_log.json`, `result.json` con mensajes, herramientas, resultados y estados. En CI actual estos archivos existen **solamente dentro del contenedor/evaluador efímero**, no son archivados ni accesibles después de cleanup; se conserva un resumen SHA256 y métricas estrictas allowlist. Sin traza íntegra un tercero puede **repetir el procedimiento** con código/modelo fijados, pero no revisar qué hipótesis, datos, decisiones y argumentos se emitieron en el episodio original. No llamar a esta ausencia «auditoría científica independiente reproducida».

## D. Alternativas existentes sin desarrollar un sistema de custodia propio

Fuentes externas verificadas el 2026-11-21: [GitHub descargar artifacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts), [REST artifacts](https://docs.github.com/en/rest/actions/artifacts), [facturación y uso](https://docs.github.com/en/actions/concepts/billing-and-usage), [uso seguro de Actions](https://docs.github.com/en/actions/reference/security/secure-use), [age (CLI/lib de cifrado mantenida)](https://github.com/FiloSottile/age) y [age-keygen](https://github.com/FiloSottile/age/blob/main/doc/age-keygen.1.ronn).

| Vía | Seguridad y disponibilidad real | Esfuerzo/costo/bloqueo |
|---|---|---|
| **1. Seguir solo resúmenes allowlist + hashes en repositorio público** | Ya funciona, bajo riesgo de filtración, sin claves/permisos ni costo facturado de runner público; permite verificación **instrumental**, no revisión integral de razonamiento/datos de episodio | No permite cerrar brecha de trazabilidad científica completa. Aceptable para calibración, **no** para afirmar hito H0 auditado |
| **2. Subir raw transcript a artifacts del repositorio público** | **NO-GO:** usuarios con acceso read al repo (público) pueden descargarlos; retención por defecto90 días, ajustable para público1–90, no equivalen a un almacén privado | Descartar sin publicación. No arreglar con «log masking» de secretos; en datos estructurados puede fallar |
| **3. Repositorio privado separado para trazas** | Restricción real de lectura a quienes tengan acceso; solución nativa de GitHub con versionado/revisión y artifacts privados. Mantener ciencia y código en repo público | Se requiere autorización de crear/usar repo privado, permisos y credencial de escritura desde workflow público (GITHUB_TOKEN actual de solo lectura NO proporciona escritura cross-repo); la facturación de runners privados depende de minutos/almacenamiento incluidos en cuenta, **cuota concreta no comprobada**, no asumir gratis |
| **4. Cifrar localmente la traza con CLI existente age a una CLAVE PÚBLICA del propietario antes de subir solo ciphertext como artifact público** | `age` soporta recipient público, decrypt con identidad privada que no se comparte con runner; solo ciphertext queda público, se conserva trazabilidad si el dueño retiene clave y archivo. Evita almacenar una clave de descifrado en Actions y conserva modelo de runner público | Requiere aprobación **explícita** para publicar ciphertext de material del benchmark, elección/gestión de clave pública por usuario y aceptación de riesgos de metadata/retención; bytes ciphertext siguen públicos, clave privada perdida = irrecoverable. Necesita gates para jamás subir raw ni registrar nombres/targets sensibles, y pruebas sintéticas; no implementar sin aprobación |
| **5. Runner local + almacenamiento privado bajo control del usuario** | No sube raw a GitHub; permite corpus privado completo, costo cloud0 si hardware ya existe | Exige configurar runner y máquina/credenciales; GitHub desaconseja un self-hosted runner adjunto a repo público sin medidas por superficie de código no confiable, costo electricidad/CPU y disponibilidad; mayor complejidad, NO es la opción por defecto |

**Selección argumentada D-0061:** mantener **por ahora** esquema 1 para no exponer privados y detener nuevos benchmarks con pretensión de H0 auditado. Para habilitar trazas completas, priorizar **evaluar opción 4 cifrado age a public key del usuario** porque no cambia backend CPU/grader ni exige almacenamiento privado adicional, **solo si el propietario autoriza expresamente publicar ciphertext y acepta custodiar la private key**. Como alternativa más conservadora evaluar opción 3 repo privado con permisos/cupos. No se guardó ningún dato sensible ni se establecieron claves en T0.53; no hay nuevo acceso ni gasto. **Futuro T0.54 requiere decisión/permiso del usuario** para habilitar un destino de trazas; hasta entonces solo se puede realizar trabajo documental o fixtures sintéticos sin datos privados. H0 sigue CORREGIR, H1/H2 no iniciados. El método no debe avanzar a pruebas que comprometan verificación de contenido original sin resolver esta decisión.
